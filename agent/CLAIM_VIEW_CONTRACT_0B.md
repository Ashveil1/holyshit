## 1. Result layers
Every view returns one outer layer:
- COMPLETE: resolution finished and, where a search is needed, the in-scope search was exhausted as section 5 requires. Only here may a status appear: SUPPORTED, CONTRADICTED, UNKNOWN, AMBIGUOUS (subject).
- OUT_OF_SCOPE: shape, predicate, negation or identity not covered. Reasons: `predicate_unsupported`, `negation_unsupported`, `shape_unsupported` (free-form value, subject-only, reference word), `identity_collision`. No evidence, counts, candidates, status, or colliding strings are shown or named.
- INCOMPLETE: a bound stopped the search before completeness. Reasons: `depth_limit`, `work_limit`. No status and no partial support or opposition is shown. Never rendered as UNKNOWN.
Output may state the configured bounds (D, W). It never states actual work counts, examined edges, or hidden identities.
Readings (0a section 6 unchanged) appear only in the COMPLETE layer. OUT_OF_SCOPE and INCOMPLETE show none.

## 2. Scope profile
Identity is exact canonical (0a section 3 canonicalization), no article stripping: "a robin" and "robin" are different identities.
In scope (stored predicate names as in the engine):
- `is-a`: positive and `not-is-a`, over the is-a chain.
- `has`: positive and `not-has`, with inheritance down is-a.
- `is-in`: direct edge plus positive transitive chaining over is-in edges only. No negation, no is-a inheritance. Asked negative is-in: OUT_OF_SCOPE `negation_unsupported`.
- `means` (B22): a positive means query considers (1) direct taught means tuples for the resolved subject and object, and (2) applicable direct built-in definitions (a built-in applies when its subject and object equal the query's), both WITHOUT chaining. Built-ins carry provenance `builtin` (section 7), count toward W when consulted, join the collision scan, and are excluded from the authoritative tuple count (R1). Asked negative: `negation_unsupported`.
OUT_OF_SCOPE `predicate_unsupported`: can, uses, produces, needs, causes, anything else. Negation is valid only for is-a and has. Phrase mapping ("is" to is-a) belongs to the A24.1 parser adapter; the view takes structured (subject, predicate, object, polarity).
No `_RULES` proofs exist in 0b. Structural is-a inheritance and is-in chaining ARE derived evidence (section 4) but are not rule-based proof and carry no guards. The guard-blocked note (F4) is RESERVED, not emitted. Future conditions: current query and path only, a guard actually blocked a candidate path AND a complete strict search found no proof for that exact proposition and polarity, naming the grounded intermediate subject, never evidence or status, never from stale `gfail`.
Hypotheses, explore assumptions, `_derive_render` and cooc hints are never read.

## 3. Resolution, identity safety, no stripped lookups
- Subject resolution (0a plus B12): the eligible targets are the exact canonical key (if it exists) and every exact taught alias whose target key exists. The key is NOT preferred. A query string that is both a key and an alias: if all eligible targets are the same key, UNIQUE; if they differ, AMBIGUOUS. Dangling aliases are ignored; every alias consulted counts toward W; no fuzzy or reading-based resolution. Done in the view before any search. B23: taught aliases resolve SUBJECTS only. Objects use exact canonical string equality: no object aliases, no fuzzy matching, no reading-based resolution.
- B9 exact-keyed index. The production view reads relations ONLY through an exact-keyed relation index keyed by the frozen canonical subject string, preserving original tuples without merging or stripping ("robin" and "a robin" are different keys). It never uses an article-stripped key, never falls back to the stripped index, and never scans all tuples. A missing, stale or inconsistent index is an IMPLEMENTATION FAILURE (fail closed, an error with no output), never UNKNOWN, never COMPLETE. That index does not exist in the engine today. Building it is a core change that needs its own design review, an Oracle mirror and the index consistency tests of section 8. This spec decision is not permission to change code. The Python Oracle holds its own exact store with the same logical budget.
- B15 index lifecycle and mutation boundary (R1). The exact index is a second representation of relation state, maintained WITH the authoritative state and never rebuilt by scanning tuples per view. ALL relation changes (create, teach, correct, forget, any mutation, load, rebuild) go through ONE controlled atomic mutation path that updates the authoritative tuples, the index buckets and the generation marker together. The view, readers and every other caller must not change relation state or index buckets outside that path. The boundary must be enforced by construction in a future implementation (relation tuples and index buckets reachable for writing only through the mutation interface, so direct tuple or index mutation is actually prevented), not merely checked by tests. Failed or interrupted mutations leave state and index consistent or both unchanged.
  Runtime checks (cheap, no global scan): the state's generation marker equals the generation the index was built for, the index exists, and the index tuple count equals the authoritative tuple count. COUNT DEFINITION: the number of stored relation tuples, counting duplicate stored tuples individually and EXCLUDING built-in definitions (those are consulted separately and counted against W when consulted). A failed runtime check is an IMPLEMENTATION ERROR: fail closed with no epistemic result (not UNKNOWN, INCOMPLETE or OUT_OF_SCOPE).
  Guarantee limits: these checks detect a missing index, a generation mismatch and a count mismatch only. They do NOT prove the index holds the right tuples (a wrong tuple replacing a correct one keeps the count, and a same-count mutation that skips the marker evades them). Correctness of index content rests on the single mutation path plus the full-comparison tests of section 8, not on a per-view check. No per-view global scan is required or allowed. The marker is change detection, not authentication. The Oracle models the lifecycle independently.
- B17 no view-time initialization. The view must not construct, rebuild, repair or lazily initialize the index, and must not create the generation marker. Build and rebuild happen only through the separately specified state lifecycle (B15). An unavailable index fails closed. Tests instrument the view for any index write.
- B18 preserved endpoints. The index stores the original tuples and original endpoint strings, with no pre-collapse or discard of distinct strings. The collision scan canonicalizes the preserved strings, so the index cannot conceal a collision.
- Collision scan covers ALL identities the view inspects: the asked subject and object, every endpoint (subject and object) of every inspected edge of either polarity, every alias key and alias target consulted during resolution, and endpoints of built-in definitions when means or built-ins are consulted. If two distinct canonical strings in that set share an article-stripped form (leading "a " or "an "), the result is OUT_OF_SCOPE `identity_collision` with no evidence and no named strings. The scan runs before COMPLETE is declared; a collision found at any point voids partial results.

## 4. Search semantics and evidence polarity (B1, B7)
Query-relative polarity. For asked (S, P, O, polarity pol): evidence whose stored polarity equals pol SUPPORTS the claim; evidence of the opposite polarity is OPPOSITION. This holds for is-a and has. Example: asked "S is-a O" with only a stored not-is-a: opposition, CONTRADICTED opposition_only. Asked "S not-is-a O" with the same store: support, SUPPORTED. Same-level evidence of both polarities gives CONTRADICTED both_sides. The truth table is 0a section 4 with P = support set and N = opposition set.
Node depth versus evidence level (B32). Node depth is a property of nodes: the resolved subject is depth 0, and a node first reached by n positive is-a hops (shortest path, visited set) is depth n. B11: is-a traversal follows ONLY positive is-a edges; a stored not-is-a edge may be evidence classified against the asked polarity but never extends traversal. Evidence level is a property of evidence, defined per predicate:
- is-a: an is-a or not-is-a edge from a depth-d node into the asked object is evidence at level d+1. A direct edge from the subject is level 1. A matching not-is-a edge at depth 8 is possible level-9 evidence (B31).
- has: a `has` / `not-has` edge for the asked object on a depth-d node is evidence at level d.
- is-in (B11): positive chain support only. Evidence found after d prior positive is-in hops is level d (a direct is-in edge from the subject is level 0). Chaining follows positive is-in edges only. A stored negative is-in edge is NOT opposition to a positive query and does not extend any chain; negative is-in queries stay OUT_OF_SCOPE.
D bounds node depth (0..8), never the evidence level number.
- means: direct only, level 0.
Nearest level: the smallest level holding evidence of either polarity. Show ALL evidence at that level in both polarities (caps as 0a). Deeper evidence is ignored and not reported. Output says: "nearest-level result, not an inventory of every reachable edge". Same-level order independence: result and ordering do not depend on insertion order.
Provenance: stored = a single stored tuple that directly states the asked claim: level-0 has/means, a direct is-a edge from the subject (level 1), a direct is-in edge. derived (structural) = anything needing an is-a hop for inheritance or two or more edges (is-a chain beyond one edge, inherited has, is-in chain). Derived evidence is dependent on every edge in its path, is never corroboration, and is distinct from `_RULES`-based proof. A subject reached via an alias keeps its provenance but notes alias resolution.

## 5. Completeness and bounds (B2, B3, B4, B8)
Own search, not `_rule_prove`, `pseen`, `memo` or first-result paths. Bounds (version 1, configured values): D=8, W=500.
- D=8 (B10) bounds is-a traversal and has inheritance, identically for is-a queries and has queries. Nodes at depths 0 to 8 may be expanded. Positive is-a edges from depth-8 nodes may be inspected (counting toward W) only to detect a depth-9 frontier. Depth-9 nodes are never expanded and never evidence. With no nearer evidence and a depth-9 frontier remaining: INCOMPLETE `depth_limit`. With no frontier: complete (UNKNOWN if no evidence). Nearest evidence at depth 8 or shallower completes without deeper search. An is-a object 9 hops away, or has evidence on a node 9 hops away, is therefore INCOMPLETE when nothing nearer exists. Positive is-in chaining is not depth-bound: W and the visited set only.
- W is one shared counter per view over ALL phases and BOTH polarities (B14: a record-examination budget only). It counts each alias entry consulted, each tuple RETURNED from an exact-keyed adjacency list and examined (one examination classifies both polarities; a repeat examination counts again), and each built-in definition consulted. It is not a bound on CPU or memory: string processing, sorting, index maintenance and index initialization are outside W. Collision checks reuse endpoints of already-read items and add no count. Exactly 500 examinations are allowed. The 501st attempted examination stops the search: INCOMPLETE `work_limit`, even if some evidence was already seen.
- NONE subject resolution: COMPLETE UNKNOWN `no_trusted_evidence`, no search. AMBIGUOUS subject: COMPLETE AMBIGUOUS `ambiguous_subject`, candidates from taught keys and aliases only, no search, no evidence. Readings (B13): NONE keeps the 0a rule exactly (B16): a reading record is selected when its canonical subject, its predicate and its canonical object equal the query's. Query polarity is NOT part of selection. Both reading sides (pos and neg) of a selected record are shown, each row carrying its side, labeled "unverified reading, not used for the answer", ordered by source, sentence, side, after eligibility, capped at 5 with the overflow count (0a). So the same readings show whether the query is positive or negative. They never affect status. 0a behavior is not altered. AMBIGUOUS shows NO readings (0a behavior preserved) and performs NO access at all to `state["readings"]` or the exclusion input (not read, parsed or validated), exactly as for INCOMPLETE and OUT_OF_SCOPE (B6). Readings never resolve a subject, pick or rank candidates, or change epistemic status. COMPLETE does not mean every reading is displayed. A reading that seems related to several ambiguous candidates adds nothing. Resolution counts toward W (alias entries read); a W overrun there is INCOMPLETE.
- Evidence found at nearest level k: COMPLETE iff both polarities of ALL evidence at level k are enumerated and classified, and every shallower level was read and held none, within D and W. Predicate-specific stopping rule (intended, tested): for an is-a query, evidence at level k lives in the tuples of nodes at depth k-1, so only nodes at depths 0..k-1 are read; depth-k nodes are NOT read. For a has query, evidence at level k lives in the tuples of depth-k nodes, so nodes at depths 0..k are read; nodes at depth k+1 are not reached. For is-in, nodes at BFS levels 0..k are read for the chain level k. No deeper search is required, and a remaining deeper frontier does not block COMPLETE. The stopping rule decides which nodes and buckets are REACHED; it does not filter inside a reached bucket (B33). Deeper nodes are not reached merely to inspect irrelevant records, but every returned-and-inspected tuple in a reached bucket consumes W whatever its predicate or polarity, including irrelevant ones, so unrelated tuples can exhaust W before a later relevant tuple is examined.
- No evidence: COMPLETE UNKNOWN only if the reachable closure is exhausted (frontier empty) within D and W. A frontier remaining past node depth D: INCOMPLETE `depth_limit`. W exceeded: INCOMPLETE `work_limit`.
- If a limit prevents enumerating the opposite polarity or all same-level evidence, the result is INCOMPLETE and NO partial support or opposition is shown.
- Cycles are cut by the visited set and never cause INCOMPLETE by themselves.
- Examination order (B24), deterministic and independent of insertion order: (1) matching alias records consulted in resolution (B44), sorted by canonical target key, then original alias string, then original target string; (2) search levels in increasing order; within a level, nodes sorted by canonical key; within a node's exact-keyed bucket, tuples sorted by (predicate, polarity, canonical object, original object string, original subject string); (3) consulted built-in definitions last, in the exact B49 order. The collision scan runs incrementally over identities as they are examined. Precedence: a collision noticed before the W or D stop gives OUT_OF_SCOPE `identity_collision`; a limit reached before any collision is noticed gives INCOMPLETE. Because the order is fixed, shuffled insertion orders give identical outer-layer results, including at the 500/501 boundary. Tests shuffle insertion orders.
- What consumes W (B28). Buckets are exact-keyed by subject only. EVERY tuple returned from a bucket and inspected is charged 1 and is examined, whatever its predicate or polarity: irrelevant tuples in a mixed-predicate bucket are NOT filtered before charging. Tuples are returned in the fixed order above, so the 501st attempted examination can fall mid-bucket. Collision scanning is aligned: a tuple's endpoint identities (subject and object) enter the collision scan exactly when that tuple is examined, and not otherwise. A predicate-split index (subject, predicate) would change this accounting and needs a contract revision. Duplicate stored tuples are each charged. Duplicates collapse to one displayed line and are never corroboration. Among several shortest paths, the displayed derivation path is the one first discovered in the fixed examination order.
- Query-identity preflight and total order (B30). BEFORE any alias work or W spending, the canonical query subject and canonical query object are checked against each other for a collision (no W charge). Only then are aliases consulted (charged), then the search in order. The sort is a total order and locale-independent: strings compare byte-wise on their UTF-8 bytes (canonical string first, then original string), never by locale or collation. Alias records sort as stated in B24 and B44.
- Built-ins (B29, B34, B35). Built-in definitions never create subject candidates and are never part of subject resolution. After a UNIQUE resolution of a positive means query, the COMPLETE `_BUILTIN_RELS` set is examined in the B24 deterministic order after taught tuples. Every examined definition costs 1 W, matching or not. Evidence comes only from definitions whose subject equals the RESOLVED canonical key and whose object equals the exact canonical query object. A matching-only lookup would need its own specified lookup and W rules. No built-ins are consulted for NONE or AMBIGUOUS. INTENTIONAL (B35): a built-in alone never resolves a subject. With no exact taught key or eligible alias target, resolution is NONE, no built-ins are consulted, and the result is COMPLETE UNKNOWN (assuming integrity validation passes and resolution fits W). A means question about a purely built-in term is therefore "no trusted support in current view" until the user teaches it.
- Subject-key universe (B36). Eligible subject keys are the union of the entity-key set (fact keys) and the subject keys of stored relation tuples. A canonical string that appears only as a relation OBJECT is not a subject key. A key with no tuples (empty bucket) is a valid UNIQUE subject and yields COMPLETE UNKNOWN. An alias target is eligible only if it is inside this universe; targets outside it are dangling and ignored.
- Empty buckets and index integrity (B40). A fact key with no stored relation tuples is still a UNIQUE subject: an ABSENT per-key bucket is an empty adjacency list, not index corruption. An explicit empty bucket gives the same result but never creates a subject whose key is outside the B36 universe. A missing or unavailable ENTIRE index still aborts (B37), even for a valid fact key. Four distinguished cases are tested: fact key with absent bucket, fact key with explicit empty bucket, non-universe key with explicit empty bucket, and missing whole index.
- W limit and collision boundary (B41). Before examining each W-charged item (alias entry, relation tuple, built-in definition), if 500 items have already been examined, stop with INCOMPLETE `work_limit` WITHOUT examining that item and WITHOUT adding its identities to collision scanning. Otherwise charge it and collision-check its identities as part of that same examination. A collision visible in the 500th examined item can therefore yield OUT_OF_SCOPE `identity_collision`; a collision visible only in the 501st item cannot, and the result is INCOMPLETE `work_limit`. This applies identically to alias entries, tuples and built-ins. Sort keys never enter collision scanning. Because the order is deterministic (B24), the outcome is the same for every insertion order.
- D-stop precision (B43). The depth-8 boundary is processed in the deterministic order, charging and collision-checking each examined tuple. For is-a queries and for the frontier test: the FIRST positive is-a edge to a previously unvisited depth-9 node, or a matching `not-is-a` edge to the asked object, establishes the depth limit. After checking that item, return OUT_OF_SCOPE `identity_collision` if it exposed a collision, otherwise INCOMPLETE `depth_limit`, and do NOT examine later boundary items. Edges to already visited nodes create no frontier (cycles via the visited set). For has queries: all required depth-8 buckets are still read to enumerate level-8 evidence, and a depth-9 frontier does NOT stop that scan; level-8 evidence gives COMPLETE even with a deeper frontier; no level-8 evidence and a frontier gives INCOMPLETE `depth_limit`; no frontier gives COMPLETE UNKNOWN; W exhaustion mid-scan gives INCOMPLETE `work_limit`. The B31 matching-negative case is effective when encountered before the depth stop. Collision-vs-depth precedence therefore follows examination order.
- Alias reachability (B44). The alias phase enumerates EVERY stored alias record whose canonical alias key exactly equals the canonical query subject. Several records with the same alias key may exist (one alias may name several targets). Matching records are charged independently in the B24 order. Non-matching alias records are NOT inspected and NOT charged. Example: 499 matching records targeting "a zebra" followed by one targeting "zebra": if both are eligible keys, the 500th target creates the collision. If an implementation's alias store is one record per alias key, the alias phase cannot reach item 500, and the contract states that explicitly instead of claiming reachability for every item type.
- Built-in definitions and their order (B49). The built-in set is exactly these four definitions (original strings; predicate `means`, positive polarity), as in `_BUILTIN_RELS` of core.holy:
  1. subject `is-in`, object `the containment relation: X is in Y says X is inside Y`
  2. subject `mean`, object `the definitional relation: X mean Y says the definition of X is Y`
  3. subject `is-a`, object `the kind relation: X is a Y says X is a kind of Y`
  4. subject `has`, object `the part relation: X has Y says Y is part of X`
  (the subject word `mean` is distinct from the predicate `means`). The order above is NOT the declaration order in core.holy; it is the B24 sort. The ordering key is the same tuple as for relation tuples: (predicate, polarity, canonical object, original object, original subject), compared byte-wise on UTF-8, with canonical = ASCII-lowercase and ASCII-whitespace-collapsed (so `X` and `Y` lowercase for the key; the original strings are kept and displayed). Declaration order never affects results (tested with shuffled declaration order). Built-ins are examined only after the taught tuples of the resolved subject (B34).
- First qualifying D-boundary item (B51). In the deterministic order (depth-8 nodes sorted by canonical key; within a node, tuples in B24 order), a tuple at the depth-8 boundary QUALIFIES iff it is (a) a positive is-a edge whose object node is not already visited (including an edge whose object is the asked object), or (b) for an is-a query only, a `not-is-a` edge whose object equals the asked object. Every other tuple in the bucket (has tuples, is-a edges to visited nodes, nonmatching not-is-a) is NON-QUALIFYING: it is charged and collision-checked when reached, and does not stop the scan. The first qualifying item stops the is-a scan only after it is charged and collision-checked. W interaction: if the qualifying item is the 500th examination it is examined, so a collision gives OUT_OF_SCOPE and otherwise INCOMPLETE `depth_limit`; if it would be the 501st examination it is NOT examined and the result is INCOMPLETE `work_limit`.
- Alias retrieval boundary (B46). Alias resolution is an exact lookup by canonical alias key that returns every matching record, without inspecting non-matching records. Each returned record is charged independently, in the B24 order, and its identities enter collision scanning as part of that examination (B41), after being charged. B50: an exact canonical-alias-key lookup is MANDATORY and there is no scan fallback. Only matching records are charged and collision-checked; nonmatching alias records are never touched, so W and collision results cannot depend on storage order or on unrelated aliases. The physical structure stays unspecified, but a structure that cannot do an exact lookup does not satisfy this contract.
- Boundary demonstrations (B47, B48). Fixtures give explicit ordered sequences for the 500/501 boundary in each W-charged kind: alias records, relation tuples, and built-ins (built-ins follow taught tuples, so an actual built-in needs enough preceding taught-tuple examinations; there are 4 built-ins, in B24 order is-in, mean, is-a, has). For each kind: first 499 items clean and item 500 collides gives OUT_OF_SCOPE; a separate case with the collision first visible at item 501 gives INCOMPLETE `work_limit`. D-stop (is-a queries) has three cases: collision at the first qualifying boundary item gives OUT_OF_SCOPE; the first qualifying boundary item is collision-free (with a clean non-qualifying tuple allowed before it) gives INCOMPLETE `depth_limit`; a collision only in a later boundary item stays unexamined and gives INCOMPLETE `depth_limit`. For has queries the depth-8 scan continues past a frontier, so a later boundary collision IS seen and gives OUT_OF_SCOPE.
- Empty buckets are semantically inert (B45). Presence or absence of an empty-only bucket changes neither the authoritative tuples nor the subject universe, and never creates a subject key. Full-index consistency compares the stored tuple multiset per canonical subject bucket, preserving original tuples and duplicates, and must not fail solely because an empty-only bucket is present or absent.
- Originals are never overwritten (B18/B42). Canonicalization is used only for comparison and ordering. It never replaces the stored original endpoint strings.
- Result-layer precedence and integrity abort (B37). Integrity failure is an explicit abort OUTSIDE the three semantic layers. Order: (1) validate query shape, predicate and polarity: unsupported input is OUT_OF_SCOPE with no index checks; (2) for an otherwise valid in-scope query, check index existence, generation and count, WITHOUT W, even when resolution will turn out NONE or AMBIGUOUS; on failure abort with no ClaimView result of any kind; (3) query-identity collision preflight (B30), subject resolution, search; (4) only after COMPLETE, the reading privacy pipeline.
- Depth-boundary negative is-a edges (B31). Defined narrowly. For an is-a query, a `not-is-a` edge on a depth-8 node whose object is the asked object is possible level-9 evidence: it is counted toward W, enters collision checking, is NOT reported, does not extend traversal, and with no nearer evidence makes the result INCOMPLETE `depth_limit`. Any other negative is-a edge at the boundary (different object) creates no frontier. For a has query, depth-9 nodes arise only via positive is-a edges, so negative is-a edges on depth-8 nodes create no frontier.
- Stored predicate and polarity normalization: the stored predicate is read as the engine's name; `not-<pred>` is polarity negative of `<pred>` and only is-a and has accept it. Other names are out of scope as in the scope profile.
- Ephemeral counter (B26): W may be an ephemeral local counter created and discarded inside one view call. Persistent engine counters, state mutation, caches and any cross-call memory are forbidden.
- Display caps (5/5/5, root 0, display depth 2, 20 nodes) are rendering caps, distinct from the internal search depth, and never decide completeness.

## 6. Purity and reading isolation (F6, B6)
The view writes nothing: no `_derive_render`, no hypothesis records, no persistent counters, no caches, no cross-call state. The only counter the view creates is the temporary W counter local to one view call (B26/B27). The view may READ generation and count metadata owned by the relation mutation lifecycle (B15) but may not create, update or persist it (B38); persistent lifecycle metadata is distinct from the ephemeral W counter. Engine calls used in tests run on an isolated deep copy with mode forced strict and leave original state byte-identical (repeatability test).
No reading-state access before COMPLETE is decided: `state["readings"]` and the exclusion input are not read, parsed or validated during resolution, search, collision scan or while computing INCOMPLETE/OUT_OF_SCOPE. Only after the layer is COMPLETE does the 0a privacy pipeline run (exclusion shape check, eligibility, order, cap, render). A test uses a poisoned readings store that fails on any access in INCOMPLETE and OUT_OF_SCOPE cases.

## 7. Built-in provenance (F8)
`_BUILTIN_RELS` means definitions appear with provenance `builtin`: "built-in definition; not user-taught; not independent evidence". Ordinary forget never removes them. A built-in plus a taught edge for the same claim are two displayed lines but never corroboration or two independent sources.
